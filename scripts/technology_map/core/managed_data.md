# SlabFlux Core: Managed Data (`managed_data.hpp`)

## 1. Architectural Overview
In a zero-allocation framework, relying on manual `malloc` and `free` (or raw pointer tracking) leads to inevitable memory leaks and Use-After-Free fatal crashes. The `managed_data<T>` wrapper provides deterministically bounded, RAII-compliant memory ownership exclusively tailored for the lock-free `spsc_pool` and `mpmc_pool` ecosystems.

## 2. RAII with Zero Allocator Overhead
Unlike `std::unique_ptr` with custom deleters (which often carry state bloat or virtual dispatch penalties), `managed_data<T>` is a strictly zero-overhead wrapper.
- It internally holds the raw pointer `T*` and an origin `pool_type*`.
- Its memory footprint is exactly two pointers (16 bytes).
- When the object goes out of scope, the destructor executes a direct, non-virtual `pool->release(ptr)` call, recycling the memory back to the specific memory arena it was born in.

## 3. Zero-Copy Conduit Transport
`managed_data` is explicitly designed to travel across `mpmc_conduit` and `spsc_conduit` lock-free ring buffers.
- When pushed into a conduit, the wrapper's move-semantics transfer ownership deterministically.
- The producer yields the pointer, and the consumer thread inherits it.
- If an event is dropped mid-flight due to an `error_arbiter` quarantine or pipeline short-circuit, the RAII destructor ensures the memory is instantly and safely returned to the pool.

## 4. Array and Batch Specializations
For SIMD processing scenarios, `managed_data` supports contiguous batch allocation via `managed_batch<T>`. 
Instead of wrapping a single pointer, it wraps an array sequence generated by `make_batch()`. Upon destruction, it executes a single, vectorized `release_batch()` instruction, returning dozens of objects to the lock-free pool via a single atomic sequence bump.
